#### Overall Impression

The main frame is now recognizably Noter: calm, warm, local, and much closer to Direction A. The biggest opportunity is hierarchy discipline. The interface currently gives sidebar commands, formatting tools, note metadata, footer metrics, view controls, backup status, and note content all persistent space. The Note is still primary visually, but the chrome is not yet quiet enough to fully disappear into writing.

#### What's Working

1. **The material system is coherent.** Light and dark surfaces now share the same notebook logic: warm frame, muted sidebar, clear editor plane, restrained yellow selection.
2. **The footer is much closer to the mock.** Lines, Words, Characters, Mode, view buttons, and `1:1` now create a real status bar instead of a centered control island.
3. **Recovery and local-first confidence are materially present.** Backup controls, Recently Deleted, Storage Recovery, and Merge Import align with the product's local-first promise.

#### Priority Issues

**[P1] Backup status uses success language before success exists**

**Why it matters**: A green dot next to `No backup yet` suggests the system is healthy, even though the user has no recovery point. This undercuts local-first trust.

**Fix**: Treat `No backup yet` as neutral/action-needed: hollow dot, muted amber dot, or no dot. Reserve green for `Up to date` after a successful export. Keep the full backup summary in tooltip or diagnostics, but make the visible footer state honest.

**Suggested command**: `$impeccable clarify Backup footer status`

**[P1] Persistent chrome is still too loud for a note-first product**

**Why it matters**: The primary task is writing or recognizing a Note. The sidebar command stack, search, note list, toolbar, metrics footer, mode controls, backup controls, and focus icon all appear at once. This creates moderate extraneous cognitive load.

**Fix**: Lower the visual weight of non-writing utilities. Make formatting tools more contextual or visually subordinate. Move `About` out of the main command stack. Consider a smaller command header closer to the mock's density.

**Suggested command**: `$impeccable quieter main frame chrome`

**[P1] Shortcut badges imply a keyboard model the UI does not fully deliver**

**Why it matters**: `N` and `/` badges look like direct shortcuts. The actual quick capture shortcut is not plain `N`, and `/` is not clearly a global shortcut. Power users will try them and lose trust if they do not work.

**Fix**: Either implement the displayed shortcuts exactly, or change badges to explicit symbols only where implemented. For quick capture, show `⌘N` / `Ctrl N` if detectable, or remove the badge.

**Suggested command**: `$impeccable harden keyboard affordances`

**[P2] Footer right-side utilities are visually present but semantically thin**

**Why it matters**: `1:1` and the diagonal focus icon copy the mock shape, but they do not yet map to a clear user need. Decorative status chrome violates the product's "every word earns its place" rule.

**Fix**: Make `1:1` a real zoom/measure state only if zoom exists. Otherwise replace the right cluster with a meaningful save state, selected Note modified date, or remove it. Rename the icon action if it remains.

**Suggested command**: `$impeccable clarify editor footer utilities`

**[P2] Mobile sidebar is usable but not thumb-first**

**Why it matters**: On mobile, the user lands in a full-height sidebar with primary actions at the top and Backup controls fixed at the bottom. This supports navigation, but not quick capture or interrupted one-handed use.

**Fix**: Give mobile a bottom-reachable primary create action or compact bottom command row. Keep Backup secondary, not competing with note creation in the thumb zone.

**Suggested command**: `$impeccable adapt mobile main frame`

#### Persona Red Flags

**Alex, power user**: Alex sees shortcut badges and immediately tries `N` and `/`. If those do not trigger creation and search focus exactly, the interface feels performative. Alex also has no visible keyboard path for moving through search results or note rows.

**Sam, accessibility-dependent user**: Sam benefits from labels and ARIA on many controls, but several controls are small or semantically vague: the note action menu icon, `1:1`, focus editor, and B/I/S toolbar controls need stronger labels/tooltips and clearer focus intent. The green dot plus `No backup yet` also communicates state partly through color and conflicts with the text.

**Casey, distracted mobile user**: Casey can use the full-width sidebar, but `New Note` is high on the screen and Backup occupies the bottom. The mobile view prioritizes system utility over fast capture in the thumb zone, which conflicts with Noter's Quick Capture promise.

#### Minor Observations

- The selected note row is recognizable, but the yellow fill still feels a little heavy compared with the mock's denser row treatment.
- Note previews are very muted; scan density is good, but recognition suffers when several rows are similar.
- `Help` in the footer is Markdown-specific, but the label reads like global app help.
- Toolbar icons are serviceable, but the B/I/S row still nudges the product toward Markdown workbench territory.
- The desktop app frame has a strong outer shell, but the editor content origin could move a little closer to the mock's top-left density.

#### Questions to Consider

- What would disappear if the app trusted the user was here to write, not configure?
- Should `Backup` be a persistent footer utility, or should only its risk states persist?
- Are the displayed shortcut badges promises, hints, or decoration?
- If the footer can only carry four concepts, which four are truly essential while writing?
- What would the frame look like if `About`, `Help`, and diagnostics were support surfaces rather than always-adjacent controls?
